# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run from the repo root — this is an npm workspaces monorepo (`backend`, `frontend`).

- `npm install` — install both workspaces.
- `npm run dev` — runs backend (`tsx watch`, port 3210) and frontend (Vite, port 5173) in parallel via `npm-run-all`.
- `npm run build` — builds backend (`tsc`) then frontend (`tsc -b && vite build`).
- `npm run typecheck` — runs `tsc --noEmit` in both workspaces.
- Per-workspace: `npm run dev --workspace backend`, `npm run build --workspace frontend`, etc.

There is no test runner or linter wired up.

The frontend dev server proxies `/api` → `http://localhost:3210` (see `frontend/vite.config.ts`). The WebSocket endpoint is `ws://localhost:3210/ws`; in dev the frontend hardcodes that host (`App.tsx`, `ActionsTab.tsx`, `CarnetTab.tsx`), in prod it uses `location.host`. (Port 3210 instead of 3001 because Windows Hyper-V/WinNAT reserves excluded port ranges — on this machine 3001–3100 — causing `listen EACCES`.)

## Architecture

Local tool for driving Playwright sessions with rotating proxies, isolated browser profiles, and per-account fingerprint spoofing. UI labels and user-facing strings are in French — preserve that when editing.

### Data layout (file-backed, no DB)

All state lives under `data/` at the repo root, read/written directly by the backend stores. **Backend code runs with cwd = `backend/`**, so all default paths resolve via `process.cwd() + '/..'`:

- `data/accounts.json` — `accountsStore` (`backend/src/accounts.ts`). Each account owns a `fingerprint` and optionally a `proxyId`. Accounts without a fingerprint are auto-upgraded on load, as are accounts without `enabled` (→ `true`). **`enabled`** is the carnet's on/off switch: off = *parked*, not deleted — the account keeps its profile, proxy and fingerprint but is hidden from **the whole `ActionsTab`** (`activeAccounts`, which also prunes it from an already-loaded selection, from a saved account group, and clears it from the picked `accountId`) and `canStartInvitations` refuses it with `compte désactivé` (backstop, since a group can still carry a parked id). Since 2026-09-18 that includes the **session picker** and the **"À commander" acceptance cards** (`parkedAccountIds`) — the operator asked for parked accounts to be invisible on that tab, so nothing there may offer one. `accounts` still holds the full list so `accountLabel` can name a parked account in a server-side skip notice, and an already-open session for one still shows in the Sessions list (hiding a live browser window would strand it). The Carnet and `GroupesTab` remain the only places a parked account appears — `GroupesTab` **keeps listing it, greyed out with a "désactivé" badge** (`Member.parked`), because a group is where you need to spot one and take it out; each account group's header also counts `N désactivé(s) à retirer` and `N actif(s) non inclus` (`trackCoverage`, accounts only — over ~100 proxies that second badge would be noise). The account-group dropdown in `ActionsTab` shows the **eligible** member count (`N sur M` when members have been parked or deleted since the group was saved), not `memberIds.length` — the raw count promised more accounts than `loadAccountGroup` actually ticks. It is excluded from `AccountInput` (so `create()` always sets `true`); the toggle goes through the generic `PATCH /api/accounts/:id` whose body is `Partial<AccountInput> & { enabled?: boolean }`.
- `data/cards.json` — `cardsStore` (`backend/src/cards.ts`). Brand is detected from the number (Visa/MC/Amex).
- `data/amazon-items.json` — `amazonItemsStore` (`backend/src/amazon/itemsStore.ts`). The scraped JCC Pokémon catalogue. Each item has `asin`, `title`, `imageUrl`, `productUrl`, `extension`, an `enabled` toggle, and an `inStore` flag (+ `lastSeenAt`). Re-import merges by `asin`, preserves `enabled`, and marks items absent from the latest scrape as `inStore:false` (never deletes them).
- `data/amazon-invitations.json` — `invitationsStore` (`backend/src/amazon/invitationsStore.ts`). Log of buy-invitation requests keyed by `accountId:asin` (`status`, `message`, `requestedAt`, `lastCheckedAt`).
- `data/account-groups.json` / `data/proxy-groups.json` — `accountGroupsStore` / `proxyGroupsStore` (`backend/src/groups.ts`, one generic `GroupsStore` class, two instances). Named groups of `memberIds` (account ids / proxy ids). The two kinds are **independent** — there is no stored link between an account group and a proxy group; a bulk action picks one of each at run time.
- `data/proxies-state.json` — soft-delete tombstones + last-test results for proxies.
- `data/playwright-profiles/<accountId>/` — persistent Chromium user-data dir per account. Override root with `PROFILES_DIR`.
- `Webshare 100 proxies.txt` (repo root) — the proxy source, parsed as `host:port:user:pass` per line. Override with `PROXY_FILE`. The file is gitignored.

Stores are class singletons (`proxyStore`, `accountsStore`, `cardsStore`, `amazonItemsStore`, `invitationsStore`) instantiated at module load; they hold state in memory and `persist()` on every mutation. Don't introduce a second instance — import the singleton.

### Session lifecycle (`backend/src/playwright/sessionManager.ts`)

`SessionManager` is the only piece that talks to Playwright. It enforces **one session per account** (`accountSessions` map) — re-creating throws.

Two launch paths:
- **With `accountId`**: `chromium.launchPersistentContext(profileDirFor(accountId), …)` so cookies/storage survive. The account's `fingerprint` drives `userAgent`, `viewport`, `deviceScaleFactor`, `locale`, `timezoneId` at context level, then `applyFingerprint()` injects `FINGERPRINT_INIT_SCRIPT` via `addInitScript` to spoof `navigator.*`, WebGL params (`UNMASKED_VENDOR/RENDERER_WEBGL`), and add canvas noise. Also sets `Accept-Language`.
- **Without `accountId`**: ephemeral `chromium.launch()` + `newContext()` — no profile, no fingerprint.

Proxy resolution: explicit `proxyId` wins; otherwise falls back to the account's `proxyId`. When a session is created with both, the account's `proxyId` is updated to match (so the last-used proxy sticks).

**Auto-login (`ensureLoggedIn`)**: after the initial navigation, both `create` and `reopen` call `ensureLoggedIn(session, account)` for account-backed sessions. It checks `isLoggedIn(page)` (reads the `#nav-link-accountList-nav-line-1` greeting — "Identifiez-vous" = logged out), and if logged out clicks the account nav link to reach the sign-in form, then runs the shared `attemptLogin()` with the account's stored `email`/`password`. On success it re-navigates to a clean page; on failure it sets `session.error` (and a `log` event) so the card shows why. No-op without credentials or when already logged in. `attemptLogin()` is the same helper the invitation runner uses.

**Account creation (`registerAmazonAccount`)**: the `amazon-register` session action (UI button "Créer compte Amazon" in `ActionsTab`, **forces headed**, requires a selected account) creates a fresh Amazon account. `create()` first calls `resetProfileForFreshStart(accountId)` — **wipes the profile dir (`rmSync`, with retries for Windows lock latency) + regenerates the fingerprint** — so each attempt is a brand-new device (a returning cookie/device is what makes Amazon flag the attempt or wrongly claim the email exists). Then: homepage → accept cookies → reach the create-account form. **The signin page has two variants**: (A) a "Créer votre compte Amazon" button (`#createAccountSubmit`), or (B) the unified email-first page — enter the email + Continue, which for a new address may pass through a "Cet e-mail est nouveau" intent page (`#intention-submit-button-announce`) before the form. A small loop clicks whichever CTA is present until `#ap_customer_name` appears (a cold `/ap/register` hit 404s — never use it). Fills `#ap_customer_name` (prénom + nom), `#ap_email`, `#ap_password`, `#ap_password_check`, submits (`#continue`), then hands off to `runRegisterVerification()` — a state-machine loop (`classifyRegister`) over: **email OTP** (resolved from Gmail via `solveOtp`/`otpMailbox`), **"Ajouter un numéro de téléphone"** (Amazon forces it, no skip), **SMS code**, captcha, logged-in. The phone step is **automated via smspool** (`backend/src/amazon/smsProvider.ts`): order a France/Amazon number (`orderNumber`), enter it, `pollSms` for the code, submit; if no SMS (FR Amazon numbers deliver only ~31% — `success_rate` from `/request/price`), it clicks "Modifier" and orders another, up to 6 tries (failed numbers auto-refund). A **captcha** is an **Arkose Labs FunCaptcha** ("casse-tête" puzzle in an `iframe.arkoselabs.com` iframe), detected by `detectCaptcha` (scans all `page.frames()` for WAF/Arkose iframes + keyword text). `solveAndInjectFunCaptcha` extracts the public key + `blob` (the iframe URL's `data=` param — a ~500-char value, the correct blob) + subdomain (`amazon-api.arkoselabs.com`), solves via **Anti-Captcha** (`captchaSolver.ts`, `FunCaptchaTaskProxyless`, passing `data: {"blob": "<param>"}`), then injects the token. The **token injection mechanism is known** (recon 2026-06-07): set the token into the hidden `#cvf_aamation_response_token`, then submit `#cvf-aamation-challenge-form` (POST `/ap/cvf/verify`; CSRF/action fields are pre-filled by the page) — implemented in `solveAndInjectFunCaptcha`. **But the solve is unreliable in practice**: Anti-Captcha solved Amazon's Arkose once (~95 s) but otherwise returns `ERROR_CAPTCHA_UNSOLVABLE` or times out (3/3 timeouts in one full run); meanwhile the Arkose session ages, compounding failures. So `solveAndInjectFunCaptcha` retries 3× with a 110 s per-attempt timeout, but **don't rely on auto-solve** — it falls back to the user solving in the **headed** window. **The reliable fix is residential proxies** (this Arkose almost never appears off datacenter IPs). Unsolvable Anti-Captcha tasks aren't billed (so the dashboard shows nothing for them). Anti-Captcha's API is **unreachable directly from this network** (TCP timeout) → `captchaSolver` routes calls through a Webshare proxy via undici `ProxyAgent` (default proxy `#1`). Datacenter proxies trigger this captcha far more than residential. `registerAmazonAccount` runs **fire-and-forget** from `create()` (the email-OTP + multi-number SMS loop can take minutes — don't block the HTTP response); progress + final outcome stream via `log`/`session.updated` (and `session.error`). Before launching, `create()` calls `resetProfileForFreshStart`. "email already used" (variant-B email step → password page) is detected and reported. Known signup obstacle: **datacenter proxies (Webshare) trigger the hard puzzle captcha frequently** — residential proxies would reduce it. `create()` routes account-backed `amazon-register` sessions here instead of `ensureLoggedIn`.

**OTP (`attemptLogin` → `solveOtp` → `otpMailbox`)**: `attemptLogin` handles the email→continue→password split-or-combined form, ticks `rememberMe`, submits, then if it lands on an OTP/MFA/CVF page (`isOtpPage` looks for `#auth-mfa-otpcode`/`otpCode`/`#cvf-input-code`/`name="code"`) it resolves the code automatically. `solveOtp` reads it from Gmail via `backend/src/amazon/otpMailbox.ts`. The actual IMAP connection lives in `backend/src/amazon/gmailClient.ts` — a **single shared connection** (`gmail` singleton, Gmail caps simultaneous connections, so don't open one per login/feature; `gmail.withInbox(fn)` runs `fn` while holding the INBOX lock so access is serialised). Both `otpMailbox` and `invitationMailbox` go through it; `gmailConfigured()` gates the path. Every Amazon account uses a `fifa10081994+xxx@gmail.com` alias so all codes land in one inbox; the per-account match is by **exact recipient header** (`To`/`Delivered-To`/`X-Original-To`), because Gmail's IMAP `SEARCH` ignores plus-addressing and would otherwise return another account's code. Codes are deduped by UID and bounded by the attempt's start time (`SINCE` is date-granular, so `internalDate` is re-checked with a 60 s skew buffer). On success the device is remembered (`rememberDevice`) and the run continues; on failure it falls back to `otp: true` so a **headed** caller can finish by hand. Requires `GMAIL_USER` + `GMAIL_APP_PASSWORD` in `backend/.env` (gitignored); `otpMailboxConfigured()` gates the whole path.

**IMPORTANT — email OTP only works when 2-step verification is OFF.** Amazon only e-mails a one-time code for *new-device verification* when 2SV is disabled. If an account has 2SV enabled (SMS/**WhatsApp**/authenticator — Amazon does NOT offer email as a 2SV method), the code goes to the phone and never reaches Gmail. `solveOtp` detects a phone challenge (`/ap/cvf/transactionapproval` text mentioning WhatsApp/SMS/"numéro de téléphone") and fails fast with an explanatory message instead of polling the inbox for 90 s. So for the Gmail-alias automation to work, the Amazon accounts must have **2SV turned off** (and the alias domain must forward to the Gmail inbox). Verified on the Lucie Martin account (2024-06): login flow reached the challenge correctly but the account had WhatsApp 2FA, so no email arrived.

**Proxy auth via `proxy-chain`**: authenticated proxies are NOT passed straight to Chromium — its native proxy-auth flow (`Fetch.continueWithAuth`) returns HTTP 407 in some environments even with valid credentials. Instead `launchContextAndPage` spins up a local `anonymizeProxy()` forwarder per launch and hands Chromium an auth-less `http://127.0.0.1:<port>` proxy. The local URL is stored on the `Session` and closed via `closeAnonymizedProxy()` in `Session.close()` (also on `reopen`). Keep this indirection when touching launch code.

**Resource blocking (`applyResourceBlocking`)**: `SessionOptions.blockResources` aborts heavy requests via `context.route` to save residential-proxy bandwidth + speed. `'light'` (font/media only, keeps images+CSS) is used for **account creation** (`amazon-register`, headed) so the page stays human-readable and a captcha remains hand-solvable. Normal sessions aren't blocked.

**Never block resources on invitation runs** (was `'aggressive'`; removed 2026-09-18 after it silently broke every request for months). Bisected on a live account, one ASIN at a time, headed and headless alike:
- *no blocking* → the click fires `POST https://data.amazon.fr/custom/highdemandproductcontracts/request-invite/<id>` → 200, button hidden, "Invitation demandée, merci !" shown, Amazon mails **"Demande d'invitation reçue"** within seconds. Acknowledged in ~1.5 s.
- *block images only* → **no request at all**. Amazon's `data-action="invite-button"` handler never runs; the page just keeps offering the button. That alone is enough to break it.
- *block image+css+font+media* (the old setting) → same, plus Playwright's `click()` times out every time (broken layout intercepts the pointer) so it always fell through to the DOM `.click()`, which also did nothing.

CSS in particular must never be blocked: **Amazon ships both branches of the invitation widget in the DOM** — the "Demander une invitation" button *and* "Invitation demandée, merci !" — and only CSS hides the inapplicable one. Without stylesheets every `innerText` check reads both states at once, so `already` detection and any text-based acknowledgement are pure noise. Bandwidth is never worth a run that requests nothing.

**Navigation (`navigateTo`)**: use `page.goto(url, { waitUntil: 'domcontentloaded' })` then a `waitForFunction` that waits for a non-empty `document.title`/`body`. This is required because Amazon, behind a proxy, first serves an AWS WAF JS challenge (~2 KB HTML that sets a cookie and reloads); returning on `domcontentloaded` alone lands on a blank challenge page. Do NOT navigate via `page.evaluate(() => window.location.assign(...))` — `waitForLoadState` resolves instantly against the already-loaded `about:blank` and the real nav never completes. On failure (commonly a dead/expired proxy → `ERR_TUNNEL_CONNECTION_FAILED`/timeout) it sets `session.error` and emits `session.updated`, so the UI shows the reason on the session card instead of a silent `about:blank`. Note: a stuck-on-`about:blank` session almost always means the proxy is down — the `Webshare 100 proxies.txt` list is static and silently expires.

### Realtime updates (WebSocket)

**All three consumers go through `frontend/src/liveSocket.ts` (`connectLive`), which reconnects** with exponential backoff (500 ms → 10 s). Never call `new WebSocket` directly in a tab: without a retry a single dropped socket leaves the page permanently deaf — the backend keeps running and emitting, the UI stays frozen on its last frame (observed 2026-09-18: ten invitation runs shown "en file d'attente" while five were actually running, because `tsx watch` had restarted the backend). A reconnect heals the UI by itself since the server opens every connection with a full `snapshot` and each consumer rebuilds from it.

A single WS endpoint `/ws` is handled by `SessionManager.attachClient`. On connect, the server sends a `{ type: 'snapshot', sessions }`. After that, every mutation emits an `Event` (`session.created` / `session.destroyed` / `session.navigated` / `session.awaiting_otp` / `account.updated` / `log`, plus the `invitation.started` / `invitation.item` / `invitation.done` / `invitation.error` progress events) broadcast to all connected clients. The frontend reconciles tab state from these events. When adding a new server-side state change that the UI should react to, emit a new `Event` variant rather than relying on polling.

### Frontend

`frontend/src/App.tsx` is a flat tabbed shell (`actions`, `amazon`, `commandes`, `carnet`, `cartes`, `groupes`, `generator`, `proxies`) — each tab is a self-contained component under `src/tabs/` that fetches via `/api/...` and listens to the WS for live updates. Tailwind + dark theme; no component library is wired up (no `components/ui/`), just Tailwind classes directly. The invitation task is triggered from `ActionsTab` (account-scoped), not the Amazon tab.

### Fingerprint generation (`backend/src/fingerprint.ts`)

`generateFingerprint()` picks one of ~6 hardcoded presets (Win10/11/macOS with viewport + GPU combos), then attaches `locale: 'fr-FR'`, `timezoneId: 'Europe/Paris'`, and a random `canvasSeed`. **Preset viewports are kept ≤ `MAX_VIEWPORT` (1440×810)** because a headed session opens the real Chromium window at the fingerprint's viewport size — bigger presets (the old 1920/2560-wide ones) overflowed a small operator screen. `accountsStore.load()` also **clamps any already-stored fingerprint** over that cap (width/height min'd down, GPU/OS/UA untouched), so raising or lowering `MAX_VIEWPORT` re-migrates existing accounts on next boot. The companion `FINGERPRINT_INIT_SCRIPT` is a self-contained IIFE string injected at context init time — it reads `window.__POKESOFT_FP__` (set just before) and patches navigator, WebGL, and canvas APIs. If you change the `Fingerprint` shape, update both the generator and the init script.

### Account generator (`backend/src/generator.ts`)

`generateAccounts({ count, baseAddress, emailDomain, excludeEmails, excludeAddresses, excludePasswords })` produces fake French identities by combining `PRENOMS`/`NOMS` lists, "jiggling" the base address (randomly adding/removing diacritics + toggling `n°` prefix to defeat exact-string dedup), and generating an 8-char password via `genPassword()` (≥1 lower/upper/digit/special, shuffled — matches the existing account password style). Output is `{ prenom, nom, email, adresse, password }`; it does **not** persist — the frontend posts the chosen rows back to `/api/accounts`. The `POST /api/generate/account` route **always seeds `excludeEmails`/`excludeAddresses`/`excludePasswords` from the current carnet** so no two accounts get an identical email, address, or password string (address dedup key = trimmed/whitespace-collapsed, case+accents kept — accent variants stay distinct on purpose). `CarnetTab`'s "Nouveau compte" modal has a **"Remplir automatiquement"** button (create mode) that pulls one generated identity into the form; re-clicking re-rolls. `GeneratorTab` shows the generated password too. `generateUniqueAddresses(count, base, exclude)` makes just address variations; `POST /api/accounts/fill-addresses { baseAddress? }` uses it to **backfill a unique address into every account that has none** (excluding all carnet addresses), surfaced as a "Remplir les adresses manquantes" button in `GeneratorTab`.

**Debug probes (`backend/src/debug/`)**: `inviteProbe.ts` drives one ASIN on one account with full request/console tracing — `npx tsx src/debug/inviteProbe.ts <asin> [--click] [--css|--no-block|--only=image,font] [--headless]` (run from `backend/`). It is what bisected the resource-blocking bug; reach for it before theorising about the invite flow. `mailProbe.ts` lists recent Amazon mails (subject + recipient) from the shared inbox. Both hit the real site on a real account — `--click` requests a real invitation.

### Amazon catalogue + buy invitations (`backend/src/amazon/`)

`storeScraper.ts` — `scrapeBrandStore()` walks the JCC Pokémon brand store. It loads any store page (the nav listing all sub-pages is identical store-wide), then visits each sub-page and keeps the ones whose breadcrumb parent is `Acheter Par Extension` (so new extensions are detected automatically). Products are read from `li[data-testid="product-grid-item"]` (ASIN in `data-csa-c-item-id`, title from `a[title]`, image from the tile's `img` srcset). Endpoint: `POST /api/amazon/import` (synchronous, ~1 min; in-flight guard). The condensed display name shown in the UI is derived **frontend-side** in `AmazonTab.tsx` (`condenseTitle`) — the full Amazon title stays stored.

`GET /api/amazon/items` enriches each item with a single `invite.available: 'yes'|'no'|'unknown'` verdict that **merges two signals** (same meaning to the user — "no invitation"): (1) **store presence** — `AmazonItem.inStore` is set by `upsertMany` on import (items absent from the latest scrape → `inStore:false`, guarded so an empty/failed scrape doesn't wipe flags); `inStore:false` ⇒ `available:'no'`. (2) **run results** — `invitationsStore.availabilityByAsin()`, **freshest observation wins**: each ASIN's records are split into two camps (gotInvite = accounts that got `requested`/`already`, vs `unavailable`), and the camp holding the **most recent** `lastCheckedAt` decides — `lastInviteAt > lastUnavailableAt` ⇒ `yes`, the reverse ⇒ `no`; one empty camp settles it directly; identical timestamps (same batch) fall back to the majority (`gotInvite >= unavailable`). Availability is a property of the *item*, so the newest check describes it best. This cuts both ways and both matter: an invitation that one account caught before it closed leaves a stale `gotInvite` that must not outvote newer `unavailable` runs (the original guard — still holds, verified on `B0GSSCWMTV`); and conversely stale `unavailable` records must not bury a newer correct verdict — which is exactly what happened when the buybox detection bug was fixed (2026-07-23), 9 old wrong `unavailable` keeping `B0GZL4L9DS` flagged "indispo". **Do not go back to a plain majority rule** — it makes every detection fix invisible until every account has re-run. The `invite` payload also carries `inStore`, `unavailable`, `gotInvite`, `checkedAccounts`, `lastCheckedAt`, `lastInviteAt`, `lastUnavailableAt`. Note `already` counts toward gotInvite although it only proves *that* account already requested, not that a new account still can — so a lone fresh `already` can read `yes` until other accounts re-check. `AmazonTab` greys + badges `no` items ("indispo invit", or "hors store" when `inStore:false`), with a "Masquer indispo invit" filter and a non-destructive "Désactiver les indispo" bulk action (`enabled:false` so they stop being requested; nothing is deleted — Amazon may re-open / the product may reappear). The import returns `{ added, updated, absent, total }`; **items are never deleted on re-import**, only flagged. The scraper reads only the brand-store product grid — it never looks at a buybox or an invite button — so the marketplace-buybox pitfall described below does **not** affect import; `inStore` means solely "present in the latest scrape".

`SessionManager.runInvitations(accountId, dryRun)` — for a chosen account, opens its persistent profile (headless, proxy) and, for every `enabled` catalogue item, requests the buy invitation. The live button state is the source of truth: `input[name="submit.inviteButton"]` ("Demander une invitation") present → click (`requested`); absent within an invitation context → `already` (skip); else `unavailable`; a `/ap/signin` redirect → `login`. **The default buybox alone is not enough**: when a marketplace seller at a higher price wins the buybox, Amazon's own (invitation-gated) offer is pushed out of it and the invite button is simply absent — the item then reads `unavailable` while it is actually requestable (verified 2026-07-23 on `B0GZL4L9DS`: buybox held by a 84,99 € marketplace offer, Amazon's own at 55,99 € hidden). So when no button is found, `processInvitation` re-opens the product as `https://www.amazon.fr/dp/<asin>?m=A1X6FK5RDHNB96` (`AMAZON_FR_MERCHANT_ID`), which **forces Amazon's offer into the buybox**, and re-looks for the button there before classifying. **Do not** try to reach the offer via the "Autres vendeurs sur Amazon" (AOD) panel — it was tried and does not work headless: `#aod-ingress-link` is present but clicking it (Playwright click, DOM `.click()`, with and without CSS blocked) fires no request at all, the `?aod=1` deep link never populates `#aod-offer-list`, and the `experienceId=aodAjaxMain` fragment endpoint 404s. Note `#all-offers-display` is a **stub container present on every product page**, so it must never be used as an "AOD is open" signal. **A click is never taken on trust (fixed 2026-09-18).** `clickInviteButton` clicks (DOM `.click()` fallback when Playwright actionability fails) and then **waits for Amazon to acknowledge** via `waitForInviteAck`: the invite button must become **invisible** (`getClientRects().length === 0`). It retries the click once, and only then records `requested`. An unacknowledged click becomes **`available`**, not `requested`.

**Visibility, never presence.** `clickInviteButton` returns early when the button is present but hidden — Amazon hides it in place after a successful request rather than removing it, and ships it on every invitation product. Counting nodes would re-click an item that is already requested, and (with CSS blocked) reading text would see both widget branches at once. The acknowledgement check is visibility-based for the same reason: it holds whether or not the page is styled.

It replaced a blind `waitForTimeout(2500)` that recorded `requested` on the strength of the click alone. That is how the resource-blocking breakage stayed invisible: **0 of 80** requests on 2026-09-18 actually reached Amazon, and the log called all 80 `requested`. (An earlier guess blamed the sleep racing the request; the bisect above disproved it — no request was ever sent.)

**Independent check: the mailbox.** A request that lands triggers a `do-not-reply@amazon.fr` mail titled **"Demande d'invitation reçue"** (distinct from the later acceptance mail, "Félicitations, vous êtes invité à passer commande!"). Counting those over a run's window is the ground truth for how many requests really went out — it is what confirmed the fix, and what proved the 80 earlier ones never happened.

**`available`** = the button is there and was not clicked: a detect-only pass, or a click Amazon never registered. A detection must **never** be written as `requested` — a dry run recording "demandées" is what made a verification pass claim 80 requests that were never made. 161 such records were relabelled `available` on 2026-09-18. The forced-offer `already`/`unavailable` message leads with `offre Amazon: …` (the decisive text) since it is truncated to 160 chars. Items with no Amazon offer at all legitimately stay `unavailable` ("Aucune offre mise en avant" / "Prix plus élevé que d'habitude"). This makes it **re-runnable** — when Amazon resets an invitation the button reappears and it re-requests. Refuses to run if a normal session is already open for the account (profile-dir lock) or another invitation run is in flight. Progress streams over the WS (`invitation.*`, each event carries `accountId`: `invitation.queued` → `invitation.started` → `invitation.item`* → `invitation.done`/`invitation.error`). Per-account isolation (separate Chromium context + proxy-chain forwarder) means runs are independent; the per-account lock (`canStartInvitations`) checks an in-flight run / open session. **Concurrency cap**: at most `SessionManager.INVITATION_CONCURRENCY` (5) runs touch a browser at once — extra runs sit in a queue with status `queued` until a slot frees (launching all at once spawned too many headless Chromium + login flows and bogged the host down). **Resilience (added 2026-09-18 after a silent mass-failure)**: navigation goes through `gotoProductPageWithRetry` (3 attempts, 2 s/4 s backoff). `gotoProductPage` now **throws** when the body never fills past the AWS WAF challenge instead of swallowing it — an empty DOM used to reach `processInvitation`, find no invite button and record a confident `unavailable` (message `offre Amazon: | buybox: `, both sides empty), which under the freshest-wins rule can bury a good item. After `MAX_CONSECUTIVE_ERRORS` (5) failures in a row the run **aborts** with `invitation.error` and leaves the remaining items untouched for a re-run: previously a few seconds of lost connectivity burned the whole rest of the catalogue at ~20 items/second and the run still reported "terminé" (observed 2026-09-15 21:43:32–33, where three concurrent runs — Audrey Roux, Sebastien Menard, Emilie Robert, three different proxies — all collapsed to `net::ERR_FAILED` within the same second, i.e. a host-side network blip, not dead proxies). Items that errored get a **second pass** at the end of the run (first-pass record kept if it fails again). `ActionsTab` shows a finished run carrying `error` counts in amber as "⚠ terminé, N item(s) en échec — à relancer" instead of a green "terminé".

**Recoverable progress**: each run's state is kept in an in-memory `invitationProgress` map (`InvitationProgress`: status `queued|running|done|error`, `done/total`, `counts`, `message`, `dryRun`) so a **front refresh doesn't lose it** — the map is sent in the WS `snapshot` (`{ sessions, invitations }`) and via `GET /api/amazon/invitations/progress`; `ActionsTab` rebuilds its per-account run state from the snapshot on (re)connect. Endpoints: `POST /api/amazon/invitations/run { accountId, dryRun?, refreshDisabled? }` (single), `POST /api/amazon/invitations/run-batch { accountIds[] | accountGroupId, proxyIds[] | proxyGroupId, dryRun?, refreshDisabled? }`, `GET /api/amazon/invitations?accountId=`, `GET /api/amazon/invitations/progress`; both routes size the run via the shared `invitationRunSize()`.

**`refreshDisabled`** (UI checkbox "Revérifier les décochés", off by default since it roughly doubles the run) also visits **disabled** catalogue items — but **detect-only**: `detectOnly = dryRun || !item.enabled`, so a disabled item is never clicked even outside a dryRun, because unchecked means "don't request". Without it a disabled item is never revisited and its verdict is **frozen for good**: a run only walks `enabled` items and a catalogue re-import refreshes `inStore` but never the run-based availability, so an item flagged `no` and then switched off (typically by the "Désactiver les indispo" bulk action) could never return to `yes`. Items with `inStore:false` are left out even then — their `no` comes from the import signal, which does get refreshed. The batch route resolves account/proxy ids from a group when given. **Proxy policy: an account's own `account.proxyId` always wins** (keeps a stable IP per account → lower detection risk); the group pool only fills accounts that have *no* proxy of their own. Pool proxies that collide with an account's own proxy are excluded (so two accounts never share one IP), and each pool proxy is consumed at most once (in order). An account with neither its own proxy nor a free pool slot runs with no proxy. The resolved proxy is passed to `runInvitations` as the override (so it equals `account.proxyId` for own-proxy accounts). Returns `{ started, skipped, proxyShortfall }` — `skipped` = busy/unknown/disabled accounts, `proxyShortfall` = **count** of accounts that needed a pool proxy but the pool was exhausted (surfaced as a notice in `ActionsTab`). `runInvitations` emits `invitation.error` (with `accountId`) instead of throwing on guard failures, since it runs fire-and-forget. `dryRun` detects without clicking. The UI is the multi-select checklist in `ActionsTab` (per-account progress keyed by `accountId`). When a navigation lands on `/ap/signin`, the runner calls `attemptLogin()` with the account's stored `email`/`password` (handles the email→continue→password split or combined form, ticks `rememberMe`, submits), then re-navigates the item and retries. `loginState` is tracked per run so the login is attempted once: if credentials are rejected → `failed`, if an OTP/CVF challenge can't be resolved from the inbox (or a captcha appears) → `otp`, and in both cases remaining items short-circuit to `login` without re-attempting. OTP itself is resolved automatically via `solveOtp`/`otpMailbox` (see the auto-login section) — these runs are headless, so the Gmail-read OTP is what makes them complete unattended. Once logged in (`ok`), the persistent profile cookies carry the rest of the run.

**Verification pass + page-detected acceptances (added 2026-09-18)**: the acceptance mail is **not always sent**, so the product page is the signal that doesn't depend on one. A new `InvitationStatus` **`orderable`** means Amazon *accepted* the invitation: in the forced-merchant context (`?m=<AMAZON_FR_MERCHANT_ID>`, i.e. Amazon's own offer) the page shows an add-to-cart (`ADD_TO_CART_SELECTOR`) and no invite button. It is only trusted there — in the default buybox an add-to-cart may belong to a marketplace seller. It is checked **before** the `/invitation/i` text test, since an accepted offer still mentions the invitation; and the early `already` return now requires *no* add-to-cart on the page, so a pending request still settles without the extra navigation while a buyable one falls through to the forced check. `orderable` counts as gotInvite in `availabilityByAsin`. UI: a third button **"Vérifier l'état"** in `ActionsTab` runs `run-batch` with `dryRun:true, refreshDisabled:true` — detect-only over every in-store item, enabled or not, requesting nothing. Results surface via `GET /api/amazon/invitations/detected-orderable` (pure store read, no browser, no mail; parked accounts filtered out) in a **"Détectées sur la page produit"** block inside the "À commander" section, refreshed on every `invitation.done`. No 72 h countdown there — the deadline is only known from the mail.

**Orderable invitations (accepted) — mail-only (`backend/src/amazon/invitationMailbox.ts`)**: separate from the *request* runner above, this detects invitations Amazon has **accepted** (= you can now place the order). Pure Gmail read, **no browser launched** (so zero detection risk). Amazon e-mails `do-not-reply@amazon.fr` with subject **"Félicitations, vous êtes invité à passer commande!"**; the body says "Vous pouvez maintenant acheter <produit> … Vous disposez de **72 heures** …" and carries a `/gp/product/<ASIN>/` link + price. `listOrderableInvitations()` scans the shared inbox (window + 2-day buffer), keeps acceptances whose age < `INVITATION_VALIDITY_HOURS` (72), drops any superseded by a later **"Invitation à acheter <produit> expiré"** mail for the *same recipient + product* (matched fuzzily — expiry mails carry no ASIN), and dedupes to the newest per (recipient, ASIN/name). Recipient alias (e.g. `julien.dupuis@a-bouchard.com`) maps to the account by `account.email`. Endpoint `GET /api/amazon/invitations/orderable` returns `{ validityHours, invitations[] }` enriched with `accountId`/`accountLabel` and catalogue `title`/`imageUrl`/`productUrl` (by ASIN); 503 when Gmail isn't configured. UI: the **"À commander — invitations acceptées"** section in `ActionsTab` (on-demand "Vérifier les mails" button + a 60 s ticker that refreshes the per-card "temps restant" countdown without re-fetching; cards coloured by urgency — red <6 h, amber <24 h, green otherwise). Each card's **"Commander"** button opens a **headed session for that invitation's account** (its persistent profile/cookies + its proxy + fingerprint + auto-login) landing straight on the product page — so the order is placed *as that account*, not in the operator's own browser. This reuses `POST /api/sessions` with `{ accountId, action: 'amazon', headless: false, targetUrl }`: `SessionOptions.targetUrl` makes `create()` navigate to that URL after `ensureLoggedIn` (overriding the return-to-homepage). If the account already has a session open, `create()` throws "déjà ouverte" and the card surfaces it (use the existing session in the Sessions list). Falls back to opening the URL in a tab only when no account could be matched.

### Order history (`backend/src/amazon/ordersScraper.ts`, `ordersStore.ts`)

The **Commandes** tab (`CommandesTab.tsx`) shows each account's past Amazon orders so you can tell **neuf** accounts (no billed order) from those that already ordered. `SessionManager.syncOrders(accountId)` opens the account's persistent profile headless (own proxy), logs in like an invitation run, then `scrapeOrderHistory` walks `https://www.amazon.fr/your-orders/orders?timeFilter=year-YYYY` for **every year the `#time-filter` dropdown offers** (Amazon only lists years since the account exists), paginated by `startIndex` (10/page). Read-only — nothing is clicked. Cards are `.js-order-card`; date/total/recipient come from `.order-header__header-list-item` (label line + value line), the id from `.yohtmlc-order-id`, items from `.item-box` (`/dp/<ASIN>` link, `.yohtmlc-product-title`, image). **The cards are decrypted client-side** (`SiegeClientSideDecryption`) — the raw HTML is useless, always read the rendered DOM. The DOM reader is a `String.raw` script string, not a function: tsx's `keepNames` wraps inner helpers in `__name(...)`, which is undefined in the page. A cancelled order ("Annulé(s)", no total) is kept but **doesn't count** — an account whose only orders are cancelled is still `neuf`. Stored in `data/amazon-orders.json` (`AMAZON_ORDERS_FILE`); a failed sync keeps the last good orders (a dead proxy must not make an account look new); `orders: null` in `GET /api/amazon/orders` = never synced. `POST /api/amazon/orders/sync { accountIds? | accountGroupId? }` (default: all enabled accounts) is fire-and-forget; progress streams as `orders.progress` / `orders.synced` and is in the WS snapshot (`orders`). It shares the invitation concurrency cap and the profile lock: a sync refuses while a session or invitation run holds the account, and vice versa.

## Environment variables

All backend-side. Loaded from `backend/.env` at startup via `backend/src/env.ts` (`process.loadEnvFile()`, Node ≥20.12 — no `dotenv` dep), imported FIRST in `index.ts` so the value is set before stores read it. `.env` is gitignored.

- `PORT` (default 3210)
- `PROXY_FILE` — path to the `host:port:user:pass` list
- `PROXY_STATE_FILE` — path to `proxies-state.json`
- `ACCOUNTS_FILE`, `CARDS_FILE` — JSON store paths
- `AMAZON_ITEMS_FILE`, `AMAZON_INVITATIONS_FILE`, `AMAZON_ORDERS_FILE` — JSON store paths for the Amazon catalogue / invitation log / order history
- `PROFILES_DIR` — Playwright user-data root
- `GMAIL_USER`, `GMAIL_APP_PASSWORD` — Gmail account + **app password** (not the account password) for reading Amazon OTP codes over IMAP. Required for auto-OTP; without them `otpMailboxConfigured()` is false and OTP challenges fall back to manual. All Amazon accounts use `+alias` addresses of this one mailbox.
- `GMAIL_IMAP_HOST`, `GMAIL_IMAP_PORT` — IMAP endpoint (default `imap.gmail.com:993`).
- `GMAIL_MAILBOX` — which mailbox the readers search (default `INBOX`; **this install runs `ALL`** — the request and expiry mails are labelled and archived out of the inbox, only the acceptance mails are left there on purpose). Gmail *labels* are IMAP folders, and a filter that ticks **"Ignorer la boîte de réception"** takes the mail out of INBOX — which would silently blind both `otpMailbox` and `invitationMailbox` (they search `from: 'amazon'` in whatever `gmail.withInbox` locks). Set **`GMAIL_MAILBOX=ALL`** to search Gmail's "Tous les messages" instead: it holds every archived/labelled message whatever the filters do. `ALL` is resolved from the IMAP `\All` special-use flag, because the folder's name is localised. A literal path (a single label) also works. Amazon's own mails, for writing filters: `do-not-reply@amazon.fr` → **"Demande d'invitation reçue"** (a request landed), **"Félicitations, vous êtes invité à passer commande!"** (accepted, 72 h), **"Invitation à acheter <produit> expiré"**; OTP codes also come `from: amazon`. `annonce@amazon.fr` is marketing and matches none of the readers.
- `SMSPOOL_API_KEY` — smspool.net API key, for the phone-verification SMS during Amazon account creation (`smsProvider.ts`). Without it, the register flow stops at the phone step for manual completion. Optional `SMSPOOL_COUNTRY_ID` (default `23` = France), `SMSPOOL_SERVICE_ID` (default `39` = Amazon), `SMSPOOL_BASE` (default `https://api.smspool.net`).
